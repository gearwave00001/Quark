# Site-packages patches (R19j) — what a fresh checkout is missing

A fresh `pip install amd-quark==0.12.post1` + `transformers==5.2.0` does **not**
contain the fixes that made the R19j export possible. They were applied directly
to the venv's `site-packages` (with `.bak_*` snapshots left behind as evidence).
This folder holds the exact diffs, generated by hashing every installed file
against its wheel's `RECORD` (all 149 distributions audited — only these 8 files
deviate from pristine) and diffing against pristine PyPI copies of the same
versions.

## Versions this was validated against

- Python **3.12**, `amd-quark==0.12.post1`, `transformers==5.2.0`
- (torch 2.13.x+rocm; see `../01-system-setup.md` for the torch/ROCm matching audit)

## The 8 patches

| Patch | Target file | What it does | Class |
|---|---|---|---|
| `01-quark-awq.py.patch` | `quark/torch/algorithm/awq/awq.py` | **[AWQ_META_FIX]** materialize accelerate-offloaded meta-shell decoder layers onto their device-map home (without it the run dies at the first CPU-spilled layer — R19h L62, R19i L56). **[AWQ_HARDEN_V3]** sqrt-safe sanitize clip (`QUARK_AWQ_SANITIZE_CLIP`, default 1e4) on calib inputs + finite outliers; **[AWQ_SANITIZE_OUT]** sanitizes the reference output after f32 fallback; **[AWQ_LOSS_NORM_V3]** candidate-aware overflow-proof loss normalization; **[AWQ-F32-SAFE/F32_FALLBACK]** fp32 recompute of suspicious layers (`QUARK_AWQ_F32_FALLBACK`); **[AWQ_CLIP_OOM_FIX]** clip-search co-tiling (`QUARK_AWQ_CLIP_TOKENS`/`QUARK_AWQ_CLIP_CO_BATCH`); **[AWQ-CAT-CPU]** stage reference-output concat on CPU (avoids ~1.28 GiB GPU peak). Telemetry: `[MEMDBG]` grid memory dumps, `[AWQ-HB]` heartbeats (what the wedge watchdog arms on), `[AWQ-NAN]` probes | **REQUIRED** (META_FIX) + robustness + telemetry |
| `02-quark-evaluation.py.patch` | `quark/contrib/llm_eval/evaluation.py` | **[LMHEAD-FIX / V2]** materialize `lm_head` when it sits on the meta device during the driver's built-in PPL eval (R16 PPL=nan root cause); V2 hardens donor selection for UNTIED heads (Huihui's head is untied) | Needed only if you run the in-driver PPL eval; not needed for vLLM-based PPL |
| `03-quark-quantization-api.py.patch` | `quark/torch/quantization/api.py` | **[EARLY-SNAP]** cloudpickle-dump the post-AWQ model when `QUARK_EARLY_SNAPSHOT_PATH` is set (banks the expensive result while context is healthy); **[PHASE-SYNC]** cuda.synchronize + log markers after freeze and after calibration (async-fault isolation) | Resume safety + telemetry |
| `04-quark-post-calibration.py.patch` | `quark/torch/quantization/post_calibration.py` | **[PHASE-SYNC]** flush after quantizer realignment | Telemetry |
| `05-quark-hw-emulation-interface.py.patch` | `quark/torch/kernel/hw_emulation/hw_emulation_interface.py` | **[EXPORT-SYNC]** when `QUARK_EXPORT_SYNC` is set: sync + input/scale tensor sanity print inside the export-time quant op (caught async illegal-memory-access at its true origin) | Debug/defensive |
| `06-quark-model-preparation.py.patch` | `quark/torch/utils/llm/model_preparation.py` | **(a)** import + load branch for `config.model_type == "qwen3_5"` via `Qwen3_5ForConditionalGeneration` — stock quark 0.12.post1 does not know this multimodal architecture; **(b)** disables the blanket "qwen3_5 MoE not yet supported" `ValueError` (`if False and …`) so DENSE qwen3_5 models can be quantized; **(c)** env-driven `max_memory` overrides: `QUARK_MAX_MEMORY_GPU_GIB` (uniform), `QUARK_MAX_MEMORY_GPU<i>_GIB` (per-GPU asymmetry — the wedge-mitigation lever, see `../01-system-setup.md`), `QUARK_MAX_MEMORY_CPU_GIB` | **REQUIRED** (a+b are hard blockers; c is the VRAM-cap knob used by the drive script) |

### Minimum set for a fresh R19-style run

`01` + `06` + `08` are the hard blockers (load path, offload materialization,
CPU-GDN). Add `07` (kernel builds). `02`–`05` are quality-safety and telemetry —
cheap to include, and several env vars in the drive script
(`QUARK_EARLY_SNAPSHOT_PATH`, `QUARK_EXPORT_SYNC`, `QUARK_AWQ_MEMDBG`, the
heartbeat-based watchdog) depend on them.

## Applying

```bash
./apply.sh /path/to/venv          # defaults to the active python's site-packages
```

It applies each patch with `patch` against the exact target file, then runs the
audit below. Expect the audit to report exactly these 8 files as "modified"
post-apply (that IS the patched state).

## Verifying (any venv)

`audit_site_packages.py` re-runs the RECORD-hash audit across every installed
distribution and prints the files that deviate from their pristine wheels:

```bash
python3 audit_site_packages.py            # audits the running interpreter's site-packages
python3 audit_site_packages.py /path/to/site-packages
```

On a pristine venv: no output. On the R19j venv: exactly the 8 files above.
Use it before a long run to confirm your environment matches what produced the
reference results, and after upgrades to catch accidental reverts.
